# Per-Region Calibration and Map Wiring — Design

## Context

This is Stage 4, the final stage, of the real-coordinate location pipeline (see
`docs/superpowers/specs/2026-08-02-location-coordinates-pipeline-design.md`). Stage 3 produced
117 calibration anchors — pairs of real world coordinates and existing schematic positions for
the same real-world entity, across all 11 surface regions. This stage fits a per-region
transform from those anchors and uses it to replace those 117 locations' hand-guessed `fx`/`fy`
with calibrated values, directly in `web/src/map/locations.ts` and
`client/src/renderer/map/locations.ts` (confirmed byte-for-byte identical, so the same edit
applies to both).

## Scope, confirmed during brainstorming

Only the 117 already-matched locations get corrected. The other ~130 `MAP_LOCATIONS` entries
(including every `great-enemy` and `evergaol` — 0/24 and 0/10 matched respectively, since boss
names don't match their grace's name) have no real coordinate source from this pipeline and stay
exactly as they are. Extracting more categories is explicitly deferred, not part of this stage.

## The transform

A full 2D affine fit per region: `fx = a·worldX + b·worldZ + c`, `fy = d·worldX + e·worldZ + f`.
Chosen over a simpler scale-only fit because it also captures any rotation between a region's
real-world orientation and its schematic orientation, at no real extra implementation cost (both
are closed-form least-squares). Confirmed during brainstorming: every surface region has at
least 3 anchors (`haligtree`'s 3 is the minimum), and 3 points is exactly enough to solve the 6
unknowns (2 equations per point) with zero residual — no region is under-determined.

## Architecture

- **`server/src/pipeline/affine-fit.ts`** — pure function:
  ```typescript
  interface AffinePoint { worldX: number; worldZ: number; fx: number; fy: number }
  interface AffineTransform { a: number; b: number; c: number; d: number; e: number; f: number }
  function fitAffineTransform(points: AffinePoint[]): AffineTransform
  function applyAffineTransform(transform: AffineTransform, worldX: number, worldZ: number): { fx: number; fy: number }
  ```
  Solves the two independent 3-unknown least-squares systems (one for `fx`, one for `fy`) via
  the normal equations, each a 3×3 linear system solved in closed form (Cramer's rule — no
  external linear-algebra library needed). Throws if given fewer than 3 points.

- **`server/src/pipeline/affine-fit.test.ts`** — TDD against synthetic points generated by
  applying a known transform to arbitrary world coordinates. Since the resulting data is exactly
  affine-consistent by construction, the fit must recover the original transform's coefficients
  exactly (zero residual), regardless of whether 3 or more points are used — this gives clean,
  exact-equality assertions rather than needing to hand-verify a lossy least-squares result.

- **`server/scripts/apply-calibration.ts`** (disposable, deleted after running):
  1. Reads `tools/msb-extractor/output/calibration-anchors.json` (117 anchors).
  2. Groups them by `regionId`, fits one `AffineTransform` per region.
  3. For each anchor, applies its own region's transform to its `worldX`/`worldZ` to get a
     corrected `{ fx, fy }`.
  4. For each of the two `locations.ts` files, processes it line by line. `locations.ts` mixes
     quoting styles for names containing an apostrophe — some use an escaped single quote
     (`'Oridys\'s Rise'`), others switch to double quotes instead (`"Ranni's Rise"`) — confirmed
     by re-reading the actual file during design, not assumed. A naive `name: 'EXACT NAME'`
     search would silently miss every double-quoted entry. Instead, each line is parsed with a
     small quote-aware helper that extracts the `name` field's value regardless of which quote
     character delimits it (matching `'((?:\\'|[^'])*)'` or `"((?:\\"|[^"])*)"`, whichever the
     line actually uses, then un-escaping the result) and compares that to each anchor's exact
     name — not a fuzzy/normalized match, since two different anchors could plausibly normalize
     to the same key and a fuzzy match here risks silently rewriting the wrong line. On a match,
     only that line's `fx: ...` and `fy: ...` numbers are replaced (a plain numeric regex, no
     quoting ambiguity there); every other line, and everything else on a matched line, is left
     untouched. Chosen over an AST-based codemod because this is replacing two numbers on
     specific, identifiable lines — a full parser is unneeded complexity for that.

## Error handling

The script fails loudly (throws, doesn't silently skip) if an anchor's `name` can't be found as
an exact-match line in either `locations.ts` file — since every anchor's name was sourced from
`MAP_LOCATIONS` in Stage 3, a missing line means the file changed since Stage 3 ran, or the
replacement logic has a bug, not a benign gap to paper over.

## Testing

Unit tests for `fitAffineTransform`/`applyAffineTransform` per above (synthetic, exact-recovery
based). No unit test for the disposable script itself — verified by running it for real (per
this project's established pattern) and then:

1. Confirming a git diff touches only lines for the 117 anchor names and nothing else. Note:
   `haligtree` has exactly 3 anchors, the minimum — its affine fit is exactly determined, so
   applying it back to those same 3 points reproduces their original `fx`/`fy` almost exactly
   (modulo floating-point rounding), meaning those 3 lines may show no change, or only a
   negligible one. The real check is "no more than 117 lines changed, and no unrelated line
   changed" — not an exact count of 117, which regions with exactly 3 anchors don't guarantee.
2. Loading the actual web map in the browser and visually checking that recalibrated pins (e.g.
   Church of Elleh, a sample of minor dungeons) still look sensible within their region — not
   wildly displaced or outside the region's own shape — since a numeric diff alone can't catch a
   transform that's technically "fit" but visually broken.
